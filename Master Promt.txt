# Локальное окружение и папка проекта

Работай исключительно в папке:

`C:\Users\Пользователь\Desktop\Hackaton`

Это корневая папка проекта. Все исходники, настройки, документация, миграции базы и конфигурационные файлы должны находиться внутри неё.

Операционная система — Windows. Пользователь работает через VS Code и может не иметь установленных языков программирования и инструментов разработки.

## 1. Сначала проверь окружение

Перед созданием проекта проверь наличие:

- Node.js LTS;
- npm;
- Git;
- PowerShell;
- доступа к `winget`.

Выведи найденные версии.

Если Node.js, npm или Git отсутствуют, установи недостающие инструменты через `winget`:

- Node.js LTS: пакет `OpenJS.NodeJS.LTS`;
- Git: пакет `Git.Git`;
- GitHub CLI при необходимости: пакет `GitHub.cli`.

Перед системной установкой запроси необходимое разрешение. Не устанавливай Python, Java, Docker или другие крупные инструменты, если они фактически не требуются выбранному стеку.

После установки повторно проверь версии. Если для обновления `PATH` требуется перезапуск терминала или VS Code, сообщи об этом пользователю одной конкретной инструкцией и продолжи после перезапуска.

## 2. Инициализация проекта

Если папка пустая, создай в ней Next.js-проект со следующими параметрами:

- TypeScript;
- App Router;
- Tailwind CSS;
- ESLint;
- папка `src`;
- alias `@/*`;
- npm как пакетный менеджер.

Название npm-пакета должно быть в нижнем регистре, например `hackaton`, даже если папка называется `Hackaton`.

Если проект уже существует, не создавай его заново. Изучи `package.json`, структуру и текущие изменения, после чего установи только недостающие зависимости.

Все npm-зависимости устанавливай локально в проект. Не устанавливай глобальные npm-пакеты без объективной необходимости.

## 3. Файлы для токенов и переменных окружения

Создай два файла:

### `.env.local`

Это локальный файл с реальными токенами. Он должен использоваться приложением, но никогда не должен попадать в Git.

Подготовь такую структуру:

OPENAI\_API\_KEY=
OPENAI\_MODEL=
NEXT\_PUBLIC\_SUPABASE\_URL=
NEXT\_PUBLIC\_SUPABASE\_ANON\_KEY=
SUPABASE\_SERVICE\_ROLE\_KEY=

Не придумывай значения и не вставляй фиктивные секреты, похожие на настоящие. Оставь поля пустыми и объясни пользователю, откуда получить каждое значение.

`OPENAI_API_KEY` и `SUPABASE_SERVICE_ROLE_KEY` разрешено использовать только на сервере. Они не должны попадать в компоненты браузера, ответы API, логи или HTML.

### `.env.example`

Это безопасный шаблон для GitHub с теми же названиями переменных, но без значений:

OPENAI\_API\_KEY=
OPENAI\_MODEL=
NEXT\_PUBLIC\_SUPABASE\_URL=
NEXT\_PUBLIC\_SUPABASE\_ANON\_KEY=
SUPABASE\_SERVICE\_ROLE\_KEY=

Добавь комментарии, объясняющие назначение каждой переменной.

Если для локального демонстрационного режима используются дополнительные настройки, также внеси их в `.env.example`.

## 4. Защита секретов

Создай или проверь `.gitignore`. Он обязательно должен исключать:

- `.env`;
- `.env.local`;
- `.env.*.local`;
- `node_modules`;
- `.next`;
- логи;
- локальные временные файлы;
- файлы IDE, не нужные всей команде.

При этом `.env.example` должен разрешаться для добавления в Git.

Перед каждым коммитом проверяй, что токены не попали в отслеживаемые файлы или историю Git. Никогда не выводи полные значения токенов в терминал или итоговый отчёт.

Если секрет случайно появился в отслеживаемом файле, остановись, убери его из проекта и сообщи пользователю, что этот ключ необходимо отозвать и создать заново.

## 5. README

Обязательно создай полноценный `README.md` на русском языке.

README должен включать:

1. Название и краткое описание сервиса.
2. Образовательную цель проекта.
3. Основной пользовательский сценарий.
4. Отличительную функцию AI Skill Gap Radar.
5. Используемый стек.
6. Структуру проекта.
7. Требования к окружению.
8. Пошаговую установку на Windows.
9. Команды запуска.
10. Настройку `.env.local`.
11. Получение OpenAI API key.
12. Создание и настройку Supabase.
13. Применение миграций базы.
14. Загрузку демонстрационных данных.
15. Запуск в demo-режиме без токенов.
16. Запуск lint, typecheck, тестов и production build.
17. Инструкцию по демонстрации жюри.
18. Инструкцию по переносу проекта в GitHub.
19. Правила безопасной работы с токенами.
20. Известные ограничения MVP.

README должен позволить другому разработчику получить проект из GitHub и запустить его без устных пояснений.

## 6. Подготовка к GitHub

Если Git ещё не инициализирован, создай локальный репозиторий в:

`C:\Users\Пользователь\Desktop\Hackaton`

Подготовь:

- `.gitignore`;
- `README.md`;
- `.env.example`;
- понятную структуру проекта;
- миграции базы данных;
- seed-данные;
- команды проверки;
- лицензию только если пользователь отдельно выберет её.

Не публикуй проект и не создавай удалённый GitHub-репозиторий без явного подтверждения пользователя.

Перед подготовкой первого коммита выполни:

- проверку содержимого Git;
- поиск случайно добавленных токенов;
- lint;
- typecheck;
- тесты, если они существуют;
- production build.

Если имя или email Git не настроены, не изменяй глобальные настройки самостоятельно. Сообщи пользователю, какие данные необходимо указать.

В конце README добавь инструкции для двух способов публикации:

- через интерфейс Source Control в VS Code;
- через GitHub CLI или обычные команды Git.

## 7. Итоговая проверка окружения

Начинай реализацию основной спецификации только после того, как:

- корневая папка подтверждена;
- Node.js и npm работают;
- Git работает;
- проект устанавливается;
- `.env.local` защищён от Git;
- `.env.example` создан;
- `README.md` создан;
- приложение хотя бы один раз успешно запущено локально.

После настройки кратко сообщи пользователю:

- что было установлено;
- где находится проект;
- какие файлы созданы;
- куда вставлять токены;
- какой командой запускать приложение;
- что ещё потребуется сделать вручную.
